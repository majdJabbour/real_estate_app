# Real Estate App — Engineering Guidelines

## Scope and sources of truth
This is a Flutter mobile recruitment assessment. Prioritize the required Figma screens, bilingual UI, real API integration, responsive phone layouts, and meaningful tests over optional features. Do not invent additional screens (including a dedicated favorites screen). Confirm the selected Figma variant and required frames before implementing UI. The developer approves each phase. Read IMPLEMENTATION_PLAN.md and the current backend API contract before working.

Backend: sibling repository `../real-estate-api`. Read its current `API_CONTRACT.md` and README for API behavior; do not edit the backend from this project without approval. The older contract may not contain the approved `/favorites/ids` extension. Copy the current contract into this repository as a delivery reference when approved, record its source revision, and resolve discrepancies before implementation. Production base URL: `https://real-estate-api-gray.vercel.app/api/v1`.

## Toolchain and workflow
Use Flutter 3.50.1 stable, Dart 3.14.0, and existing pubspec dependencies and lockfile. Inspect installed package APIs and documentation rather than assuming older versions. Preserve material_ui and the current scaffold conventions unless a verified reason requires a change. No dependency changes without approval. Use Riverpod generator, hooks where useful, Freezed and json_serializable, Dio, go_router, Firebase Auth and Google Sign-In. Do not add cloud_firestore, custom token storage, or responsive packages. Inspect git status and existing code before each task. State a concise plan, implement the approved phase, run checks, report actual results and stop. Do not fabricate successful tests or reviews.

## Architecture
Use pragmatic feature-first layered architecture. Presentation depends on application state; application depends on domain contracts; data implementations satisfy repository contracts and handle DTOs and remote data. Keep domain independent of Flutter widgets, Dio and Firebase SDK. Use explicit provider-based dependency injection; no service locator or unnecessary use-case wrappers. Group home, explore, filters and details under properties. Separate authentication, favorites, profile and settings when justified. Keep common networking, errors, configuration, localization, responsive policies and design tokens in core. Create files only when needed. Prefer small widgets, immutable state, descriptive names, snake_case filenames and idiomatic Dart. Use generated providers and models consistently; do not hand-edit generated files. Commit generated Dart source needed for reproducible builds; verify generation produces no unexpected diff. Never commit build output or credentials.

Screen files are composition roots and must not declare additional custom widget classes. Screen-specific widgets belong in their feature’s widget directories. Keep widgets reused within a feature in that feature’s shared widget directory. Feature-independent components may live in application-shared widgets or the design system. Keep simple Flutter layout primitives inline and avoid unnecessary extraction and premature abstraction.

## Configuration and networking
Use a typed configuration with `String.fromEnvironment('API_BASE_URL', defaultValue: 'https://real-estate-api-gray.vercel.app/api/v1')`. Validate HTTPS for production; local overrides are developer-only. Base URL is public, not a secret. Ensure Dio URL joining preserves `/api/v1`. Centralize timeouts, JSON decoding, response-envelope validation and mapping to typed failures. Map offline, timeout, cancellation, malformed JSON, unexpected responses, HTTP and stable API error codes to localized UI messages; never display raw stack traces. Send Accept-Language on localized requests; invalidate locale-sensitive caches and reject stale responses after language changes. Never log tokens or sensitive headers. Retry only when appropriate, with bounded behavior; no automatic loops. Avoid unnecessary network requests. Do not require auth for public property calls.

## State and properties
Use generated Riverpod providers and AsyncNotifier where mutable asynchronous state is appropriate; pure derived providers for computed state. Use auto-disposal deliberately, retain shared session and relevant tab state, cancel obsolete requests and guard against out-of-order completions. Avoid provider writes during build. Distinguish initial loading, refresh, pagination, error and empty results. Keep existing data visible during appropriate refresh or next-page errors. Use independent home section queries and detail-by-ID queries. Parse summary and detail DTOs according to the current contract; no fabricated fields or hardcoded property content. Server performs search, filters, sorting and pagination; never fetch all properties to implement client filtering. Debounce search (initial proposal 350 ms), reset page on query/filter/sort/locale changes, preserve query on load more, prevent concurrent duplicate page loads, deduplicate by ID and respect hasNextPage. Retry the failed page without discarding valid items.

## Filters
Load filter options from the server. Global bounds and histogram come from API; no hardcoded Figma prices. Handle null/equal bounds and empty histogram safely. Render bucket counts with CustomPainter or native widgets; no chart dependency. Draft filters are distinct from applied filters. Apply on Set Filter, reset pagination, dismiss without changes on cancel. Reset draft only until applied. Types are comma-separated stable IDs, OR within types and AND between categories; rooms are minimums, ranges inclusive. Zero minimum imposes no constraint. Display currency and area unit correctly. Do not recompute global histogram from loaded property pages.

## Authentication and favorites
Use Firebase client SDK for session and Google Sign-In; use installed google_sign_in API. Restore auth state, handle cancellation, errors and logout. Register Android/iOS in existing Firebase project using actual app IDs, not guessed values. Never put Admin credentials in Flutter. Obtain Firebase ID tokens for protected endpoints only; on unauthorized response allow at most one appropriate forced token refresh and retry, guard session changes, and do not loop. Never use Google access tokens as Firebase ID tokens. Handle unauthenticated users browsing public properties; request sign-in for protected actions. Clear private state on logout/account switch.
Fetch `/favorites/ids` after authentication. Maintain one immutable Set<String> scoped to verified account/session. Derive heart state from membership; no isFavorite field in public property models. Use selective subscriptions for individual hearts. PUT/DELETE are idempotent. Optimistically update, rollback on failure, prevent conflicting per-ID mutations, and ignore stale results from prior sessions. Distinguish unknown/loading/error from confirmed empty favorites. Do not create a favorites page. Verify actual live Google login and persistence on device before claiming success.

## Localization and accessibility
Use gen_l10n with ARB files for all visible static text, semantic labels, errors and empty/loading states. Support en/ar, switch without restart, persist selection with shared_preferences and restore at startup. Default English unless approved otherwise. Use Directionality from localization, EdgeInsetsDirectional, AlignmentDirectional, start/end and directional icons; do not force LTR globally. Preserve numeric, phone, currency and mixed-script legibility using appropriate locale formatting and localized strings. Stable enum keys map to localized labels; dynamic text comes localized from API. Use accessible labels, sufficient contrast, touch targets around 48 logical pixels where feasible, system text scaling, keyboard and focus handling. Do not disable text scaling to hide layout problems.

## Design system and responsiveness
Read DESIGN_SYSTEM.md once extracted. Use selected Figma frame and verified colors, fonts, spacing, radii, borders, shadows and assets; never invent them as measured values. Reference frame width 430 logical pixels is a design reference, not a fixed screen size. Use native LayoutBuilder, constraints, Flexible/Expanded, Wrap, slivers, AspectRatio, SafeArea and scrollable content. Centralize responsive decisions; no global proportional scaling or fixed screen height. Proposed widths: compact <360, phone 360–599, tablet >=600, expanded >=840. Prefer two property columns on regular phones where content fits; compact layouts may use one column. Larger screens may use additional columns and a centered max-width layout. Derive columns from available content width and tested card minimums. Tablet adaptations are optional beyond required phone support. Verify 320, 375, 390 and 430 widths, landscape, Arabic/English and enlarged text. Preserve readable font sizes and avoid clipping, overflow and nested unbounded scrolling. Use real licensed assets; record sources and licenses. Do not draw fake status bars or device home indicators. Handle broken images with accessible placeholders. Every visible action must work or be clearly disabled/omitted with an explicit documented scope limitation.

## Navigation
Use go_router and a stateful shell only where actual Figma tabs require persistent state. Keep routes typed/centralized as appropriate. Preserve back behavior, selected locale, list scroll state and filter state. Do not create tabs or features absent from approved screens. Avoid auth redirect loops; allow public browsing if scope permits. Test navigation and session changes.

## Tests and quality gates
Write focused unit tests for DTO/envelope parsing, error mapping, filters/query serialization and session races; provider tests for pagination, debounce, favorites rollback and locale changes; widget tests for loading/error/empty states, Arabic/English, directional layout, responsive widths and critical actions. Use fake repositories and SDK abstractions; normal tests must not depend on real accounts or network. Use Flutter integration_test SDK only if approved/needed. Compare screenshots to Figma before claiming visual parity. Do not chase arbitrary coverage percentages.

### Platform verification

Use the existing Android emulator for routine development, runtime verification, and screenshots. Prefer Android hot reload or hot restart when sufficient. Perform a full Android rebuild only when native configuration, dependencies, or bundled resources require it.

Run only the relevant routine verification commands:

- `dart format --output=none --set-exit-if-changed lib test`
- `flutter analyze`
- `flutter test`
- `git diff --check`

Preserve iOS compatibility and avoid unnecessary changes to iOS configuration. Defer the iOS Simulator, `flutter build ios`, Xcode builds, and iOS runtime verification to the final assessment delivery phase. Apply this policy to every subsequent phase unless the developer explicitly requests otherwise.

## Git and documentation
Use small, truthful Conventional Commits after each approved cohesive change. Review git diff and staged files; include pubspec.lock. Never fabricate history, rewrite existing commits, or automatically push/commit without explicit developer approval. Report suggested commit message and files. Update AI_USAGE.md with actual tools, prompts or summaries, affected components, verification and real developer modifications/rejections. Do not invent rejected suggestions. README must cover setup, SDK, packages and reasons, architecture, API URL, Firebase setup, language and testing, screenshots or demo, assumptions and limitations. Never include tokens, service-account files or private keys. Verify Firebase client config is intentionally shareable and document setup; Admin credentials remain backend-only.

## Definition of done
Approved scope implemented, appropriate tests pass, formatting/analyze pass, no unrelated changes, documentation updated, limitations stated, and developer review completed before the next phase. Prioritize delivering the actual Flutter task over extra architecture or optional features.
